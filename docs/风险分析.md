# WeChat NewUI v0.2 风险分析

> 对象：`C:\git\wechat_chat_ui`，tag `v0.2`（`89fd040`），10 个 Java 文件、约 3000 行。
> 方法：静态审查（逐文件读源码 + 全量 API 检索），**无真机运行、无反编译比对**。
> 结论按“发生概率 × 影响”分级；`P0` = 真机日常使用前必须处理。

---

## 0. 一句话结论

模块**确实没有**网络、文件、支付、账号、消息相关代码（已全量检索确认），但“只 hook 聊天页、只动 UI”的自我描述与实现不符：实际有 **20 个 hook 点**，其中包括一个**进程级 `android.view.View.setVisibility` 全局 hook**，以及每 600ms 对整棵 View 树做一次“删除 Toolbar / 删除 TaskBar header”的破坏性遍历。

因此最高风险不是“偷数据”，而是：

```text
1. 把微信自己的 View 树拆坏 → 崩溃 / 空白 / 列表错位（不可预测）
2. 主页调试 dump 把会话标题与消息预览写进 logcat（确定的隐私缺陷）
3. 公开仓库里的 debug 签名密钥 → 可伪造“同签名”更新包
```

---

## 1. 实际 hook 面 vs 文档描述

README 写的是“只 Hook `ChattingUI` 生命周期”。实际 `HookEntry` 注册了 20 个 hook：

| # | Hook 目标 | 类型 | 作用域 |
|---|---|---|---|
| 1-3 | `ChattingUI.onCreate/onConfigurationChanged/onDestroy` | 生命周期 | 聊天页 |
| 4-6 | `LauncherUI.onCreate/onConfigurationChanged/onDestroy` | 生命周期 | 主页 |
| 7 | `ChatFooter.r1(int)` | 混淆方法 | 聊天输入栏内部 |
| 8 | `HomeUI.u(Activity, View)` | 混淆方法 | 主页边距 |
| 9 | `FindMoreFriendsUI.N1()` | 混淆方法 | 发现页 padding |
| 10 | `androidx...ActionBarOverlayLayout.onLayout` | 框架组件 | 主页 |
| 11-13 | `ActionBarContainer/Toolbar/ActionMenuView.setVisibility` | 组件 | 主页 |
| 14 | **`android.view.View.setVisibility`** | **bootclasspath 全局** | **整个微信进程** |
| 15-16 | `ConversationListView` / `ConversationRecyclerView.attachViewToParent` | 核心列表 | 主页 |
| 17 | `ActionBarOverlayLayout.draw` | 绘制 | 主页 |
| 18 | `DrawStatusBarFrameLayout.dispatchDraw` | 绘制 | 主页 |
| 19-20 | `ChattingUI/LauncherUI.onResume` | 生命周期 | 两页 |

直接引用的微信类共 15 个，全部属于 UI 层（`ChattingUI`、`LauncherUI`、`HomeUI`、`FindMoreFriendsUI`、`ChatFooter`、`ConversationListView`、`TaskBarContainer`、`DrawStatusBarFrameLayout`、`FrostedContentView` 等）。

**评价**：没有越界到消息/支付/网络，这点是可信的；但 `ConversationListView`、`TaskBarAnimController`、`ChatFooter` 属于微信核心交互，改坏的后果远大于普通 UI。

## 2. 高危发现

### F1. 全局 `View.setVisibility` hook（P0）

`HookEntry.java:372-405` 用 `classLoader = null` 挂了 `android.view.View.setVisibility`：

```java
XposedHelpers.findAndHookMethod("android.view.View", null,
        "setVisibility", int.class, new XC_MethodHook() { ... });
```

影响：

- 微信进程内**每一次** `setVisibility` 调用都经过 Xposed 桥 + 字符串判断 + `getRootView().getContext()`；
- 判断条件是“类名含 ActionBarContainer/Toolbar/ActionMenuView + context 链含 LauncherUI”，**任何用 LauncherUI context inflate 的对话框、悬浮窗、菜单里的 Toolbar 都会被打成 GONE**；
- 与第 11-13 项重复挂载，语义叠加。

虽然比 hook 整个 `Activity` 温和，但这是**框架级热路径**，是“所谓安全边界”里最名不副实的一条。建议只保留精确的 3 个类 hook。

### F2. 每 600ms 拆一次 View 树（P0）

`HomeGlassHook.updateGeometry()` 由 `tick` 每 600ms 调用一次（`HomeGlassHook.java:73-82`、`989-1001`）：

```java
hideLegacyBars(decor);
removeLegacyBars(decor);     // 递归删除所有 ActionBarContainer / Toolbar / ActionMenuView
removeTaskBarLine();         // 删 cxv 里的 1px 线
removeTaskBarHeader();       // 直接 removeView(TaskBarContainer 的 fake top bar)
```

`removeLegacyBars`（`:530-550`）会**真的把微信的 ActionBarContainer、Toolbar 从 decor 树里 removeView**，而 `ActionBarOverlayLayout.mActionBarTop`、`WindowDecorActionBar` 仍持有这些引用；`removeTaskBarHeader`（`:315-343`）直接删 ListView header 的子 View，却没有 `removeHeaderView`，ListView 的 `FixedViewInfo` 仍指向它。

后果（未真机验证，但属于确定性结构破坏）：

- 微信后续 `show()/layout()` 可能重新 add 一个仍被认为已挂载的 View → `IllegalStateException: child already has a parent`；
- ListView 布局/滚动时 header 引用悬空 → NPE 或首屏错位；
- 每 600ms 与微信自身的布局代码（文档称 `FindMoreFriendsUI` 每 100ms 重设 padding）互相打架 → 抖动、闪烁、掉帧；
- `updateGeometry()` 还被 `actionBar` 的 `OnLayoutChangeListener` 调用（`HomeGlassHook.java:234-240`），而它内部又在 `removeView`/`setPadding`，存在 **layout → 回调 → 再 layout** 的循环风险。

这是当前代码里**最可能造成“用着用着就崩/白屏”**的一处。更稳妥的做法是 `setVisibility(GONE)` + 改 LayoutParams，而不是 `removeView`。

### F3. 把 `TaskBarAnimController.V1` 置空（P1）

`HookEntry.java:416-430` 在 `attachViewToParent` 之后：

```java
Object controller = XposedHelpers.getObjectField(param.thisObject, "m");
XposedHelpers.setObjectField(controller, "V1", null);
```

`V1` 是 TaskBar 滚动动画持有的 ActionBar 引用。置空后如果动画代码没做空判断，滚动/下拉时就会 NPE；如果有空判断，只是动画失效。**两种结果都未经验证**，而这是主页最核心的滚动路径。

### F4. 聊天页 ActionBar 被“搬家”，销毁时没搬回（P1）

`ChatGlassHook.reparentActionBar()`（`:528-553`）把 `ActionBarContainer` 从 `ChattingUILayout` 里 `removeView` 后 `addView` 到 `contentFrame`。这打破了 AppCompat “ActionBar 必须挂在 ActionBarOverlayLayout/其宿主里”的假设（代码注释自己也承认会 ClassCastException）。

`destroy()`（`:1251-1273`）只移除了三个 chip、销毁了 renderer，**没有把 ActionBar 移回原父容器**，也没有移除 `statusScrim`、`navFiller`、`onGlobalLayoutListener`、`OnScrollChangedListener`。配置变化时 `attach()` 会先 destroy 再重建，旧 scrim 可能残留叠加，listener 会重复累积。

### F5. 对 `ChatFooter` 内部字段做“手术”（P1）

- `HookEntry.java:165-212`：把 `V2`/`T2` 按 0.15 英寸缩小，直接改 `z` 的高度，并调用私有 `setPortHeighPx()`、`C()`；
- `ChatGlassHook.java:292-308`：把 `footerPanel` 高度**写死 170dp**，并反射写 `p0`。

输入栏面板高度与输入法、表情、语音、平板/折叠屏形态强相关。固定 170dp 在小屏会裁切，在折叠屏会留白；`r1` 是混淆方法名，换版本后可能指向完全不同的逻辑，**盲改字段比不改更危险**。

### F6. 主页调试 dump 把会话文本写进日志（P1，隐私，确定性）

`HomeGlassHook.java:226-232` 在 attach 后 6 秒执行：

```java
dumpTree(decor, 0, new int[]{0});
```

`dumpTree`（`:681-719`）对最多 180 个 View 输出：

```java
if (view instanceof TextView) {
    label = " text=" + ((TextView) view).getText();
}
```

主页 decor 树里包含 `ConversationListView` 的会话项，于是**联系人昵称、群名、最后一条消息预览会被写进 `WeChatGlassDump` 日志**。这类日志会被 LSPosed 管理器保存、被 `adb logcat`/bugreport 读取，且没有任何 debug 开关保护。

同一文件 `dumpTop(toolbar)` 只输出标题“微信”，风险较小；`ChatGlassHook.dumpTree` 只输出类名/坐标/背景，不含文本。

### F7. 公开仓库里的调试签名密钥（P0，供应链）

- `debug.keystore` 被 git 跟踪（v0.2 及历史提交都有），口令是公开的 `android`；
- `build.ps1:57-75` 用这个 keystore 给“发布版” APK 签名；
- `versionCode` 恒为 `1`。

组合后果：任何人拿到仓库即可用**同一证书**签一个 `versionCode=2` 的 APK；Android 只校验“包名 + 签名证书 + 更高 versionCode”，会把它当作正常升级接受。用户从第三方渠道拿到这种包时无法从签名上分辨真假。

密钥已进入 git 历史，删文件无效，**必须换新密钥并作废旧密钥**。

### F8. 持续整窗截图（P2，隐私）

`GlassRenderer` 每 2 帧（约 30fps）把整个 `decor` 画进 1/8 缩放的 Bitmap（`:82-97`、`:146-160`），用于取玻璃背景。

- 捕获内容包含聊天页全部可见文字/图片，只存在于内存，`recycle()` 及时，**没有落盘、没有网络**（已检索确认）；
- 但它在聊天页可见期间持续运行，属于“在聊天软件里开了个录屏循环”，且每次 `createBitmap` 都新分配约 160KB，30fps 下 GC 压力明显。

实际泄漏面很小（无 IPC、无文件、无网络权限），但它把“模块一旦被扩展就能偷内容”的门槛降得很低，建议加节流与“仅滚动时捕获”。

## 3. 中危发现

### F9. 没有任何微信版本闸门

- 13 个硬编码资源 ID（`0x7f0a...`，共 14 处引用）；
- 20 个混淆类/方法/字段名（`r1`、`x2`、`V2`、`T2`、`p0`、`V1`、`h/i/m`、`f1484n`、`u`、`N1`、`d`）；
- 全仓库没有 `versionCode == 3182` 之类校验。

换到 8.0.80 后，最坏情况不是“hook 失败被 try/catch 跳过”，而是**同名方法语义变了、字段还在但含义不同**，于是静默改错布局。混淆名 hook 本质上是“按地址下钩子”，没有语义保证。

### F10. 600ms 全树反射遍历（性能）

- `ChatGlassHook.tick` → `EdgeForce.apply()`：递归整棵 decor 找 `EdgeToEdgeWrapperLayout`，反射读写 4 个字段、重设 padding、改状态机、`invalidate()`；
- `HomeGlassHook.tick` → `updateGeometry()`：同上再加 `clearTopPaddings`、`clearAncestorPaddingForLists`、`applyListTopInset`、`removeLegacyBars`、`removeTaskBarHeader`。

即页面静止时也每 600ms 走一遍上千个 View + 反射。叠加 30fps 捕获，属于持续耗电与掉帧源。

### F11. 失败不是原子的

`tryInstall()` 先做副作用（`clearChatBackgrounds`、`applyStatusBar`、`Ui.clearActionBarBackground` 永久清空 AppCompat 的 `mBackground`），再校验 footer/scroll 是否找到；找不到就 150ms 后重试，3 秒后放弃。放弃时微信的顶部栏已被透明化/隐藏，但 chip 没建出来 → **半成品界面，且没有恢复路径**。

### F12. 与其他模块冲突（文档自己点名）

架构报告要求“不关闭 `mmliquidglass`”。两个模块都在改同一个 `decor`/`ActionBarContainer`，LSPosed 下 hook 顺序不确定，结果不可预期（重复模糊、互相覆盖 padding、渲染递归）。代码里没有任何冲突检测。

### F13. 文档与实现偏差

“只 Hook ChattingUI 生命周期”“已移除全局 hook”“只影响两个页面”——都不准确。做安全评估的人如果只看 README，会严重低估影响面。

## 4. 正向发现（确实做对的部分）

| 项 | 证据 |
|---|---|
| 无任何权限 | `AndroidManifest.xml` 没有 `uses-permission` |
| 无组件暴露面 | 无 Activity/Service/Receiver/Provider |
| 无网络/文件/进程/剪贴板/设备信息 API | 全量检索 `Socket`、`HttpURL*`、`FileOutputStream`、`Runtime`、`ClipboardManager`、`getDeviceId` 等，0 命中 |
| 无编译期微信依赖 | 只 import Android + Xposed，微信类全部字符串反射 |
| 作用域最小 | `xposedscope` 只有 `com.tencent.mm`，且只对 owner user 生效（`myUid()/100000 == 0`） |
| EtE 白名单 | `GlobalEdgeToEdge` 只放行 `LauncherUI` / `ChattingUI` |
| 不碰支付/消息 | 引用的 15 个微信类全是 UI |
| hook 有兜底 | 每处 `findAndHookMethod` 都有 try/catch，类不存在时不会直接崩 |

| ID | 风险 | 概率 | 影响 | 等级 |
|---|---|---|---|---|
| R1 | 微信风控/封号（ToS + Xposed 特征） | 中 | 高 | 高 |
| R2 | 拆树导致崩溃/白屏/列表错位（F2/F3/F4） | 中高 | 高 | 高 |

| R4 | 伪造同签名更新包（F7） | 低（需分发/第三方渠道） | 高 | 高 |
| R5 | 微信升级后静默改错（F9） | 高（换版本必现） | 中 | 中高 |
| R6 | 与其他模块冲突（F12） | 中 | 中 | 中 |
| R7 | 耗电/掉帧（F8/F10） | 高 | 低中 | 中 |
| R8 | 半成品界面无法恢复（F11） | 中 | 中 | 中 |
| R9 | 全局 hook 误伤对话框（F1） | 中 | 中 | 中 |

R1 说明：微信用户协议禁止修改客户端，Xposed 模块被检测到可能封号/限制登录。本模块把 `com.wechatglass.*` 类加载进微信进程、使用 `XposedBridge`，属于可被检测特征；UI 类模块历史上被批量处置过。**这是无法通过改代码消除的残余风险，只能用小号 + 最小化特征。**

## 6. 处置建议

### P0（真机日常使用前）

1. **删除所有文本 dump**：`HomeGlassHook.dumpTree` 的 `text=` 分支、`dumpTop` 的 `getText()`；或整体加 `if (!DEBUG) return`。
2. **换发布签名**：生成独立 release keystore（口令不进仓库），`build.ps1` 改为从环境变量读取；旧 `debug.keystore` 作废并停止分发用它签的包。
3. **加版本闸门**：入口处校验 `PackageInfo.versionCode == 3182`，不符直接不装 hook（而不是靠 try/catch）。
4. **去掉第 14 项全局 `View.setVisibility` hook**，只保留精确三类。
5. **用 `GONE` 替代 `removeView`**：`removeLegacyBars` / `removeTaskBarHeader` 改成不可见 + 零高度，或干脆保留但 `alpha=0`。

### P1

6. `destroy()` 完整复位：ActionBar 移回原父容器、移除 scrim/navFiller、反注册两个 listener。
7. 安装改事务式：先解析并校验全部引用，通过后再改；失败时不动微信原有 UI。
8. 捕获节流：只在滚动/布局变化后捕获一帧，复用 Bitmap，空闲时停掉 frame loop。
9. 加总开关与安全模式：模块设置里可一键停用；捕获异常时自动降级为“只改背景不改结构”。
10. `ChatFooter` 相关 hook 用白名单结构校验（字段类型 + 类名 + 方法返回类型）再改，否则跳过。

### P2

11. 修正 README/文档，如实写明 20 个 hook 点与核心类引用。
12. 建立真机测试矩阵（见下）；至少覆盖深色、横屏、分屏、输入法、返回手势、工作资料。
13. 与 `mmliquidglass` 做共存检测：检测到同名 View 特征时提示冲突或自动让位。
